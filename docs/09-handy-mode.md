# 09. ハンディモード設計（日ノ出茶屋を起点に）

2026-09-26 初版、同日 日ノ出茶屋の運用回答を反映。細かい調整は試験運用で詰める。

## 前提（長谷川さん確定）

- **ハンディ = スタッフ各自のスマホ**。客のQR注文は使わない（スタッフ内部のみ）
- **スタッフのアカウントは1人1つ**
- **ハンディで注文するのはドリンク**。料理はコースで、アラカルトの料理は口頭で伝える（システムに入れない）
- **ドリンクこそ厨房タブレットに出す**。厨房タブレットは Android か iPad。**プリンターは不要**
- **会計はUSENレジ**。連携できない以上、**本システムでは金額を持たない**（お通し等の調整もレジ打ち込み時に行う）
- **相席は無いが、卓移動はあり得る**
- **売切は厨房画面から手動で切り替える**
- **ドリンク台帳と連動するのは通常の日本酒メニューだけ**。それ以外のドリンク（プラスアルファの商品）は本システムで登録し、品数はかなり多い
- USENレジとの連携は保留
- **DBは店舗間で共有のまま**（方式B維持）。既存の店舗間隔離を前提にする
- 店舗ごとの切替は `stores.order_mode`（`'qr'` / `'handy'`）で行う

## 全体像

```
スタッフのスマホ (/handy)                 厨房タブレット (/kitchen)
  卓一覧 → 来店受付                         ドリンクの伝票を大きく表示
  卓画面 → ドリンク注文 → 送信 ──0.1秒──▶   作って渡したら「提供済み」
  卓移動 / レジ用の注文一覧 → 卓を閉じる
                 │
                 └─ place_order（冪等・卓の開閉）＋ step20 の即時通知 ＝ 既存の核をそのまま使う

                                          売切の切替 ──▶ スマホの注文画面に即反映
オーナー (/admin)  … メニュー・卓・設定（今の管理画面。handyモードでは金額・在庫・QRの欄を隠す）

ドリンク台帳（日ノ出茶屋のドリンク管理Worker / Cloudflare D1）──▶ 「日本酒」カテゴリへ一方向に反映（M3）
それ以外のドリンク ──▶ /admin のメニュー管理で登録（品数が多いので、まとめて登録できるようにする）
```

## 流用するもの（既存の核）

| 既存 | ハンディでの使い方 |
|---|---|
| `place_order` / `submit_order_direct` | 注文確定。スタッフの代理注文(proxy)として送る。冪等・閉じた卓の拒否もそのまま |
| step20 の即時通知 | スマホ → 厨房タブレットへ約0.1秒 |
| `KitchenDisplay` | 厨房タブレットの画面。提供済み・呼び出し表示もそのまま |
| 来店受付（`open_table`、step17） | 席に案内したら卓を開く。閉じた卓には注文できない |
| 代理注文のロジック（`submitProxy`/`addUnit`/`cancelUnit`） | 注文入力・1個追加・取消 |
| オプション（step15） | 「グラス／1合／ボトル」「ロック／水割り／お湯割り」などの選択に使える |
| `close_table` | 卓を閉じる。金額は0円のまま、**何が何杯出たか**の記録として残る（ドリンクの売れ筋を後から見られる） |

## 画面

### スタッフのスマホ `/handy`（片手操作・縦持ち前提、金額は一切表示しない）

1. **卓一覧**: 卓をタイルで表示。空席／着席中（経過分）／厨房で作っている杯数／呼び出しあり、が一目で分かる
   - 空席をタップ → 来店受付 → そのまま注文入力へ
2. **卓画面**: この卓のドリンクと提供状況、「追加注文」「卓移動」「レジ用の一覧」ボタン。明細の取消（−）・1杯追加（＋）
3. **注文入力**: 種類の切替（日本酒・ワイン・焼酎…）＋**検索**（品数が多いため）。品目タップで数量＋、シートで飲み方・量（オプション）と**備考**。
   下部の「n点 送信」→ 確認 → 送信 → 卓画面へ戻る
   - 送信は一度だけ（冪等キー）。電波が悪くて失敗しても、同じ内容で再送すれば二重にならない
4. **卓移動**: 移動先を「空いている卓」から選ぶ → 確認 → この卓の未会計のドリンク・来店時刻をまるごと移し、元の卓は空席に戻す。
   厨房タブレットの伝票の卓名もすぐ変わる。相席は無いので、埋まっている卓は選べない
5. **レジ用の一覧**: この卓のドリンクを品目ごとに集計して表示（品名・杯数・飲み方）。USENレジに打つときに見る。
   「レジで会計した」→ 確認 → 卓を閉じる

### 厨房タブレット `/kitchen`（Android / iPad のブラウザ、ホーム画面に追加して使う）

- 今の厨房ディスプレイだけを全画面で表示（タブ無し）。文字を大きめに
- 画面が消えないようにする（Wake Lock。iPad の Safari・Android の Chrome とも対応）
- 通知音は既定ON。ブラウザの決まりで「開いた後に一度画面に触れる」まで音を鳴らせないため、起動時に「タップして開始」を出す
- 作って渡したら「提供済み」を押す（誰が押すかは試験運用で決める）
- **売切の切替**: 厨房画面の「売切」ボタンからメニュー一覧（種類の切替＋検索）を開き、品目ごとにオン・オフ。
  切り替えた瞬間にスタッフのスマホの注文画面で「売切」になり選べなくなる。
  送信と行き違いになっても、`place_order` が売切の品を拒否するので厨房には届かない（スマホに「売り切れです」と出る）

### オーナー `/admin`

- 今の管理画面のまま。handyモードでは、メニューの金額・在庫数の欄、QR発行、客のQR注文の案内を隠す
- **まとめて登録**: 品数が多いので、1行1品で貼り付けて一括登録できるようにする（例: 「焼酎 / 富乃宝山」の形。カテゴリと品名だけ、金額・在庫は無し）

## アカウントと権限（個人スマホを使うための要）

個人のスマホは紛失・退職・持ち帰りがあるため、**画面の出し分けだけでなくDB側で権限を絞る**。
`staff.role` 列（`owner / staff / kitchen`）は schema.sql に既にあり、今は未使用なのでこれを使う。

| できること | owner | staff（ハンディ） | kitchen |
|---|---|---|---|
| 卓一覧・来店受付・注文・取消・卓移動・レジ用の一覧・卓を閉じる | ○ | ○ | − |
| 厨房表示・提供済み | ○ | ○ | ○ |
| 売切の切替（厨房画面から） | ○ | ○ | ○ |
| 閉じた卓の履歴（ドリンクの売れ筋）を見る | ○ | − | − |
| メニュー（品名・カテゴリ・オプション）・卓・店舗設定の変更 | ○ | − | − |
| スタッフの追加・削除 | ○（よこでじ経由） | − | − |

- 実装: `staff_role()`（`staff_store_id()` と同じ作り）を足し、履歴の閲覧・メニュー/設定の書き込みRLSに「owner のみ」を加える。RPC（`close_table` 等）にも同じ判定を入れる
- 売切は `set_sold_out(p_item, p_sold_out)` RPC で切り替える（自店舗の品目の `sold_out` 列だけを書き換える専用の入口）。
  メニュー表の書き込み権限そのものは owner だけに残すので、staff・kitchen のアカウントからは品名や値段を変えられない
- 1人1アカウント。誰が注文を取ったかを `orders.created_by` に残す。辞めた人は `staff` の行を消せば即座に何も見えなくなる（全RLSが `staff_store_id()` 経由のため。2026-09-24に本番で確認済み）
- ログインの持続: 今は12時間操作が無いと自動ログアウト。個人スマホでは毎日のログインが手間になるので、長さは試験運用で決める

## DBの変更（小さく、既存を壊さない形で）

| 変更 | 目的 |
|---|---|
| `stores.order_mode text default 'qr'` | 店舗ごとのモード切替 |
| `stores.track_stock boolean default true` | 在庫を数えない店（日ノ出茶屋）では `place_order` が在庫の確認・減算をしない。売切の切替だけ効く。今の作りは在庫0で注文不可のため必要 |
| `order_items.note`（**列は既存・未使用**） | 備考。`place_order` が受け取るようにするだけ |
| `orders.created_by uuid` | 注文を取ったスタッフ |
| `move_table(p_store, p_from, p_to)` RPC | 卓移動を1トランザクションで（移動先が空席のときだけ。未会計の注文・来店時刻を移し、元の卓を閉じてトークンを更新） |
| `set_sold_out(p_item, p_sold_out)` RPC | 厨房画面からの売切の切替（`sold_out` 列だけ） |
| `staff_role()` と owner限定のRLS | 上の権限表 |
| handyモードの店では客注文（proxyでない注文）と `open_session` を拒否 | QRを使わない店に客経路の穴を残さない |

金額は持たない（メニューの価格は0円のまま）。いずれも既定値のままなら今の店（QR注文）の動きは変わらない。

## ドリンク台帳との連携（日ノ出茶屋専用のカスタマイズ第1号）

日ノ出茶屋にはLINEで写真を送るとボトルを登録するドリンク台帳（Cloudflare D1 `hinode-drinks`）があり、
**欠品になると台帳から行が消える**運用になっている。**連動させるのは通常の日本酒メニューだけ**
（台帳が品書きの「通常」日本酒を作っている部分。高単価の品書きや他の種類は連動しない）。

- 台帳に載った通常の日本酒 → 注文メニューの「日本酒」カテゴリに出る。台帳から消えた（欠品）→ 注文メニューからも消える
- 役割分担: **台帳は「メニューに載っているか」を決め、売切は厨房画面の手動切替が決める**。
  同期が売切を勝手に解除したり付けたりしない（瓶が空いた時点で厨房が売切にし、後でLINEで欠品処理すると品目ごと消える流れ）
- それ以外のドリンク（プラスアルファの商品。品数が多い）は /admin のメニュー管理で登録する。同期はそれらに一切触れない
- 反映の仕組み（台帳側から知らせるか、こちらから定期的に取りに行くか）は実装時に決める
- これは日ノ出茶屋だけの違いなので、「店舗ごとの差し替え口」に置く最初の部品になる

## USENレジとの連携（保留）

**現状（2026-09-26調査）**: USENレジが公式に連携している注文システムは、すべてUSEN自社製
（USEN ハンディ／Mobile Order／Tablet Order 等）。外部との連携は予約台帳・会計ソフト・売上管理・
受発注などに限られ、**公開APIや外部の注文システム向けの窓口は見当たらない**
（出典: USENレジ「サービス連携」ページ、Food Deploy の記事。USENは外部連携を「順次拡充」としている）。

当面は「レジ用の一覧」を見て打ち込む。連携の問い合わせは保留（長谷川さん判断）。
連携できることになったら、品目・数量・卓はすでに持っているので、送る側の準備は揃っている（金額はUSEN側の商品マスタに任せる）。

## 店舗カスタマイズとの関係

ハンディは「どの店でも選べるモード」として共通の核の上に作る。日ノ出茶屋だけの違い（まずはドリンク台帳との同期）は
店舗ごとの差し替え口に置く。先に汎用の枠だけ作ると何を差し替えるべきか外れやすいので、実際の違いが出た部分から切り出す。

## 試験運用で決めること（急がない）

- 台帳のボトルの注文単位（グラス／1合／ボトル）と飲み方の選択肢
- 「提供済み」を押すのは厨房か、運んだスタッフか
- 自動ログアウトまでの時間
- 厨房タブレットで、ドリンク以外（口頭で伝えた料理）も控えとして打ちたいか
